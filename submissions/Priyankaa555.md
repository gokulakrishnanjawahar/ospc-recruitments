## Finding 1 — Missing Note Ownership Validation (IDOR)

- **Severity:** Medium

- **Affected file and line(s):** `src/server.js:41-47`
- **Affected route or feature:** `GET /api/notes/:id`

- **Evidence:** The route checks whether the requester is authenticated and whether a note with the requested ID exists. However, it does not verify that the note belongs to the authenticated user. During local testing, I signed in as Alex and requested `/api/notes/202`, which belongs to Sam. The endpoint returned Sam's note title and body.

- **Impact:** An authenticated user can access other users' notes by changing the note ID in the request. This exposes information that should be restricted to the note owner.

- **Recommended mitigation:** After retrieving the note, verify that `note.owner === user.id` before returning its contents. Return an appropriate error response when the note does not belong to the requester.

## Finding 2 — Mass Assignment Allows Privilege Escalation

- **Severity:** High

- **Affected file and line(s):** `src/server.js:58-65` (mass assignment); `src/server.js:68-72` (admin access impact).

- **Affected route or feature:** `POST /api/profile` and `GET /admin`

- **Evidence:** The profile update handler passes user-supplied properties to `Object.assign(user, changes)` without restricting which fields can be modified. During local testing, while authenticated as the fictional member Alex, I submitted a JSON request containing `{"role":"admin"}`. The response showed Alex's role as `admin`, and I could subsequently access `/admin` and view the synthetic training flag.

- **Impact:** An authenticated user can modify a privileged account property and obtain administrative access, exposing functionality and information restricted to administrators.

- **Recommended mitigation:** Use an explicit allowlist of editable profile fields, such as `displayName`. Never accept authorization-related fields, including `role`, from ordinary profile-update requests. Enforce role changes through a separate, properly authorized administrative process.

## Finding 3 — Predictable Session Tokens Allow Account Impersonation

- **Severity:** High

- **Affected file and line(s):** `src/web.js:31-42`

- **Affected route or feature:** Session authentication; routes that rely on `getUserFromRequest()`, including `GET /dashboard`

- **Evidence:** The session token is generated by Base64URL-encoding a username combined with a fixed string. The request handler decodes the cookie and trusts the username without verifying a cryptographic signature or looking up a server-side session. During local testing, I constructed the predictable token for the fictional user Sam, set it as the `sid` cookie, and accessed the dashboard as Sam without authenticating as that user.

- **Impact:** An attacker who understands the token format can construct a session token for another known username and impersonate that user. This can expose the victim's data and provide access to functionality available to that account.

- **Recommended mitigation:** Use cryptographically secure, unpredictable session identifiers backed by server-side session state, or use appropriately signed and validated tokens. Do not derive authentication credentials from usernames and fixed strings. Set suitable cookie attributes, including `HttpOnly` and `Secure` when using HTTPS, and provide a reliable session invalidation mechanism.

## Finding 4 — Stored and Reflected Cross-Site Scripting (XSS)

- **Severity:** High

- **Affected file and line(s):** `src/server.js:38` (stored XSS); `src/server.js:75-80` (reflected XSS); `src/web.js:10-13` (HTML page rendering).

- **Affected route or feature:** `GET /dashboard`, `GET /search`, and `POST /api/profile`

- **Evidence:** The dashboard inserts the stored `user.displayName` directly into an HTML heading. The search route also inserts the user-controlled query into HTML without context-appropriate escaping. During local testing, I submitted HTML through the profile update endpoint and observed it being interpreted as markup on the dashboard. I also tested a script payload through the search query and observed JavaScript execution in the local browser.

- **Impact:** Malicious HTML or JavaScript can execute in another user's browser when that user visits an affected page. Depending on the victim's privileges and the application's behavior, this could allow unauthorized actions or exposure of information accessible to the victim.

- **Recommended mitigation:** Apply context-appropriate output encoding to all untrusted values inserted into HTML. Prefer safe DOM APIs and automatic template escaping. Validate input where appropriate, but do not rely on input validation as a replacement for output encoding. Consider a restrictive Content Security Policy as an additional defense.
