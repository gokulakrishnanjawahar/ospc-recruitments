## Finding 1 - Mass Assignment and Privilege Escalation

- Severity: High
- Affected file and lines: src/server.js, lines 58–65 and 68–72
- Affected route or feature: POST /api/profile and GET /admin
- Evidence: The profile endpoint uses Object.assign(user, changes) to apply submitted properties directly to the user object. I logged in as Alex, sent {"role":"admin"}, and the API changed my role to admin. After that, I accessed /admin, which displayed the synthetic training flag OSPC{synthetic_training_flag}. This confirmed that I could access the admin-only page after elevating my privileges.
- Impact: Regular users can elevate their own privileges and gain access to administrator functionality.
- Recommended mitigation: Whitelist the profile fields users are allowed to update. Sensitive properties such as roles should only be changed through a separate, properly authorized process.

## Finding 2 - Predictable Session Tokens

- Severity: High
- Affected file and lines: src/web.js, lines 31–41
- Affected route or feature: Login and session authentication
- Evidence: Sessions are generated by Base64URL-encoding the username together with a static string. The validation logic decodes the token and trusts the username inside it without checking it against a legitimate session store. I constructed a token for Sam locally without logging in, and the app treated me as Sam.
- Impact: An attacker who knows the token format can construct accepted session tokens and impersonate other users without their passwords.
- Recommended mitigation: Use cryptographically secure, unpredictable session IDs tracked server-side. Implement appropriate session expiration and revocation when users log out.

## Finding 3 - Reflected XSS in Search

- Severity: Medium
- Affected file and lines: src/server.js, lines 75–79; src/web.js, lines 10–13
- Affected route or feature: GET /search
- Evidence: Search queries are inserted directly into the HTML response without output encoding. Entering HTML into the search field showed that the browser parsed it as markup. A JavaScript test payload also executed in the browser.
- Impact: Attackers could craft malicious links that execute JavaScript in a victim's browser when the victim opens them. The potential impact depends on the victim's access and the application's functionality.
- Recommended mitigation: Apply context-appropriate output encoding to untrusted data before inserting it into HTML. An auto-escaping templating engine can help prevent this type of issue.

## Finding 4 - Broken Object-Level Authorization in Notes API

- Severity: Medium
- Affected file and lines: src/server.js, lines 40–47
- Affected route or feature: GET /api/notes/:id
- Evidence: While logged in as Alex, requesting /api/notes/101 returned Alex's note. Requesting /api/notes/202 without changing accounts returned Sam's note. The backend looks up notes by ID without checking whether the authenticated user owns the requested note.
- Impact: Authenticated users can access other users' private notes by guessing or iterating through record IDs.
- Recommended mitigation: Check that the authenticated user is authorized to access the requested note before returning its contents.

## Finding 5 - Missing Session Cookie Security Attributes

- Severity: Low
- Affected file and lines: src/server.js, line 30
- Affected route or feature: POST /login and session cookie configuration
- Evidence: The login response's Set-Cookie header included Path=/ and SameSite=Lax, but did not include the HttpOnly or Secure attributes.
- Impact: Without HttpOnly, client-side JavaScript may be able to read the session cookie, increasing the risk if an XSS vulnerability is present. Without Secure, the cookie may be sent over unencrypted HTTP connections. Testing was performed locally, so exposure over a real network was not established.
- Recommended mitigation: Configure production session cookies with HttpOnly, Secure, and an appropriate SameSite policy. These attributes improve cookie security but do not fix predictable session-token generation.

## Review notes

- How I approached the review: I reviewed the Node.js source code and tested the local application using the built-in demo accounts and sample data. I checked profile updates, notes access, session creation, search behavior, and cookie headers.
- Assumptions or limitations: Testing was performed strictly against the local training application with fictional data. No live production system was tested. Severity ratings are based on the behavior observed locally and may differ in a real deployment. The cookie finding identifies missing security attributes; it does not independently demonstrate a successful cookie theft attack.
