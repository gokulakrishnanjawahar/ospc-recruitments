# Security Assessment

**Date:** 2026-10-10

## Finding 1 — Changing the User Role

- **Severity:** High
- **Affected file and line(s):** `src/server.js` — `/api/profile` handler.
- **Affected route or feature:** Profile update and admin page.
- **Evidence:** The code uses `Object.assign(user, changes)` to update the user's details. It accepts the submitted properties without checking whether the user is allowed to change them. The admin page checks the user's role before allowing access.
- **Impact:** A normal user might be able to change their role to admin and access the admin page.
- **Recommended mitigation:** Allow users to update only permitted fields, such as their display name. Do not allow them to change their own role.

## Finding 2 — Accessing Another User's Notes

- **Severity:** High
- **Affected file and line(s):** `src/server.js` — `/api/notes/:id` handler.
- **Affected route or feature:** Viewing notes.
- **Evidence:** The code checks whether the user is logged in and whether the requested note exists. However, it does not check whether the note belongs to that user before returning its contents.
- **Impact:** A logged-in user might be able to view another user's notes by changing the note ID in the request.
- **Recommended mitigation:** Check that the note belongs to the logged-in user before showing its contents.

## Finding 3 — Unsafe Search Input

- **Severity:** Medium
- **Affected file and line(s):** `src/server.js` — `/search` handler.
- **Affected route or feature:** Club directory search.
- **Evidence:** The search value is added directly to the HTML response in the search box and results heading. The code does not show any escaping of this input.
- **Impact:** A specially crafted search value might be treated as HTML or JavaScript by the browser.
- **Recommended mitigation:** Escape the search value before adding it to the HTML response.

## Finding 4 — Predictable Login Session Token

- **Severity:** High
- **Affected file and line(s):** `src/web.js` — `makeSessionToken()` and `getUserFromRequest()`.
- **Affected route or feature:** Login and session handling.
- **Evidence:** The session token is created from the username and a fixed string using Base64URL encoding. When checking the session, the code decodes the token and uses the username without checking a signature or a server-side session record.
- **Impact:** Someone who knows a demo username might be able to create a token and sign in as that user without knowing their password.
- **Recommended mitigation:** Generate random session IDs that cannot be easily guessed. Store sessions on the server and check them whenever a user makes an authenticated request.

## Finding 5 — Missing Cookie Security Settings

- **Severity:** Low
- **Affected file and line(s):** `src/server.js` — `/login` handler.
- **Affected route or feature:** Login cookie.
- **Evidence:** The session cookie uses `Path=/` and `SameSite=Lax`, but it does not include the `HttpOnly` or `Secure` attributes.
- **Impact:** Without `HttpOnly`, JavaScript running on the same site may be able to read the cookie. Without `Secure`, the browser is not instructed to send the cookie only over HTTPS.
- **Recommended mitigation:** Add the `HttpOnly` attribute and use `Secure` when the application runs over HTTPS.
