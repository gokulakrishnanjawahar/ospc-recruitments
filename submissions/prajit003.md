Finding 1 — Broken Access Control in Notes API (IDOR)
- Severity: Medium
- Affected file and line(s): src/server.js, lines 41–47
- Affected route or feature: GET /api/notes/:id
- Evidence: While logged in as the fictional user Alex, I requested /api/notes/202 and received the note titled “Club idea,” belonging to the demo user Sam.
  The route checks authentication but does not verify whether the requested note belongs to the authenticated user.
- Impact: An authenticated user may read another user's notes by changing or guessing a note ID.
- Recommended mitigation: Check note ownership or explicit access permissions before returning note contents.

Finding 2 — Mass Assignment of Privileged Profile Fields
- Severity: High
- Affected file and line(s): src/server.js, lines 58–65
- Affected route or feature: POST /api/profile
- Evidence: While logged in as Alex, I submitted the JSON body {"role":"admin"}. The endpoint returned HTTP 200 with the role set to admin.
  The dashboard subsequently displayed Alex as an admin. The route copies submitted properties onto the user object without restricting which fields can be modified.
- Impact: An ordinary user can change their role and may gain access to administrative functionality.
- Recommended mitigation: Allowlist editable profile fields and reject unauthorized role changes. Enforce authorization checks on every administrative operation.

Finding 3 — Predictable Session Token Generation and Validation
- Severity: High
- Affected file and line(s): src/web.js, lines 31–40
- Affected route or feature: Session token generation and authentication
- Evidence: Source-code review shows that the session token is generated by Base64URL-encoding a predictable string containing the username and a fixed demo secret. 
  The authentication code decodes the token and extracts the username without verifying a cryptographic signature or validating a server-side session.
- Impact: Someone who knows the token format may be able to construct a token for another demo user and impersonate that user. 
  A successful authentication bypass has not been independently confirmed.
- Recommended mitigation: Use cryptographically secure, unpredictable session identifiers with server-side validation, or securely signed tokens with verified integrity and expiration. 
  Invalidate sessions during logout.

Finding 4 — Reflected HTML Injection in Search
- Severity: Medium
- Affected file and line(s): src/server.js, lines 75–79
- Affected route or feature: GET /search?q=...
- Evidence: I entered <i>OSPC-TEST</i> into the search field. The results heading rendered OSPC-TEST in italics instead of displaying the HTML tags literally.
  The search query is inserted into the generated HTML without appropriate escaping.
- Impact: User-controlled HTML can be interpreted in the search results page. If executable JavaScript can also be injected, this could lead to reflected cross-site scripting.
  JavaScript execution has not been demonstrated.
- Recommended mitigation: Escape user-controlled input before inserting it into HTML. Prefer safe rendering methods such as textContent and use context-appropriate output encoding.

Finding 5 — Session Cookie Missing Security Attributes
- Severity: Low
- Affected file and line(s): src/server.js, around line 30
- Affected route or feature: Login session cookie (sid)
- Evidence: Chrome DevTools showed that the sid cookie does not have the HttpOnly or Secure attributes enabled. Its SameSite attribute is Lax.
- Impact: Without HttpOnly, same-origin JavaScript can read the session cookie, increasing the impact of a successful XSS attack.
  Without Secure, the browser is not instructed to restrict the cookie to HTTPS connections. The impact of the missing Secure attribute depends on the deployment environment.
- Recommended mitigation: Enable HttpOnly and Secure for production HTTPS deployments and retain an appropriate SameSite policy. Invalidate sessions securely during logout.
